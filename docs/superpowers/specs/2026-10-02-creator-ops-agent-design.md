# 海外创作者合作 Agent 演示项目设计

## 项目目标

本项目是面向千原传媒 Agent 应用工程师岗位的可运行作品。它演示如何把创作者筛选、匹配、沟通和内容检查组成一个有数据基础、人工确认、调用日志和可重复评测的内部 Web 工作流。

项目首先服务于面试演示和个人学习，不处理真实客户数据，也不向真实创作者发送消息。第一版必须能够离线运行；用户配置 DeepSeek API Key 后，同一套流程可以切换到真实模型。

## 目标用户

主要用户是负责海外创作者合作的中文业务同事。内部界面使用中文，生成给海外创作者的邀约邮件和合作 brief 使用英文。

## 核心演示场景

用户载入一个虚构的海外品牌营销项目，导入创作者 CSV。系统清洗并去重数据，使用确定性条件筛选候选人，再让模型根据项目 brief 和检索到的历史资料解释匹配度。用户选择创作者，生成英文邀约邮件，经人工批准后标记为可发送。最后，用户粘贴一份创作者交付内容，系统检查其是否满足项目要求，并展示模型调用日志、成本和固定评测结果。

## 第一版范围

### 项目 Brief

用户可以创建、编辑或载入示例项目。项目至少包含：

- 品牌和项目名称
- 目标市场与语言
- 目标平台
- 产品和目标受众
- 营销目标
- 创作者类别
- 粉丝量范围
- 单个创作者预算和总预算
- 必须交付的内容
- 内容限制与检查规则
- 截止日期
- 自由文本 brief

### 创作者数据

用户可以导入 CSV，查看解析结果，并按市场、平台、类别、粉丝量、互动率和报价筛选。系统识别：

- 平台与账号相同的重复记录
- 缺少账号、市场、报价等关键字段的记录
- 超过配置期限的旧报价
- 无法解析的数值或日期

示例数据包含约 30 名虚构创作者，并故意包含少量重复、缺失和过期数据。

### 智能匹配

匹配分为两步：

1. 普通代码和 SQL 执行硬条件筛选及基础评分，包括市场、平台、类别、粉丝量和预算。
2. 模型只处理通过硬条件的候选人，输出结构化的匹配分数、推荐理由、证据和风险。

模型不得覆盖硬条件结果。界面必须区分规则评分和模型评分，并展示模型引用的检索资料。

### 沟通草稿与人工确认

系统为已选择的创作者生成英文邀约邮件和合作 brief。草稿保存为待审批状态。用户必须明确批准后，系统才能把草稿标记为“批准发送”。第一版不连接真实邮件服务，也不提供自动发送按钮。

### 内容检查

用户粘贴创作者交付文本和相关元数据。系统根据项目 brief、内容规则和检索资料输出：

- 已满足要求
- 缺失要求
- 风险或疑点
- 建议修改内容
- 采用的规则来源

结果是辅助判断，不自动通过或拒绝交付。

### 日志、成本和评测

每次模型调用记录用途、提供商、模型、开始时间、耗时、输入与输出 token、估算成本、结果状态和安全的错误摘要。日志不得保存 API Key。

固定评测集包含 20 个案例：

- 10 个创作者匹配案例
- 10 个内容检查案例

匹配案例记录人工期望进入推荐列表的创作者，命中率按期望创作者是否进入前五名计算。内容检查案例记录期望问题标签，问题识别率按标签召回率计算。系统还展示结构化输出成功率、平均响应时间和估算成本。评测数据使用虚构内容，结果可以重复运行。

## 页面结构

### 总览

显示当前项目、创作者总数、有效候选人数、待批准草稿、内容风险、最近模型运行和估算成本。

### 项目 Brief

提供结构化字段和自由文本 brief 的编辑与保存，并支持恢复示例项目。

### 创作者库

提供 CSV 导入、清洗摘要、筛选器、异常标记、数据来源和更新时间。

### 智能匹配

显示规则结果、模型评分、推荐理由、证据、风险和人工选择状态。

### 沟通与交付

生成和编辑英文邮件与合作 brief，执行人工批准，并提供内容检查入口。

### 日志与评测

显示模型调用、错误、token、成本和固定评测结果。

## 技术架构

项目采用单体 Web 应用：

- Python 负责业务逻辑
- FastAPI 提供页面路由和 JSON API
- Jinja 模板、原生 CSS 和少量原生 JavaScript 构成前端
- SQLite 保存业务数据和调用日志
- SQLite FTS5 负责小规模文本检索
- DeepSeek 提供真实模型能力
- 模拟模型保证离线开发和演示

单体架构减少部署和调试成本。第一版不引入 React、任务队列、缓存服务、向量数据库或独立前后端部署。

## 数据模型

### campaigns

保存项目结构化字段、自由文本 brief、状态和时间戳。

### creators

保存姓名、平台、账号、国家或地区、内容类别、粉丝数、互动率、估算报价、币种、语言、邮箱、数据来源、来源更新时间、备注和数据质量状态。

平台与标准化账号组成唯一标识。重复记录保留来源更新时间较新的非空字段，不用空值覆盖已有数据，并生成清洗摘要。

### matches

保存项目与创作者关联、硬条件结果、规则评分、模型评分、推荐理由、证据、风险、人工选择状态和更新时间。

### drafts

保存关联项目、创作者、草稿类型、英文主题、正文、审批状态、批准时间和更新时间。

### content_reviews

保存项目、提交内容、提交元数据、结构化检查结果、人工状态和时间戳。

### knowledge_docs

保存历史 brief、合作规则和内容检查规范，包括标题、类型、正文、来源标签和更新时间。FTS5 索引用于检索相关段落。

### model_runs

保存调用用途、提供商、模型、运行模式、token、耗时、估算成本、状态和错误摘要。原始 API Key 和完整敏感请求不得保存。

## 模型接入

应用通过配置项选择 `mock` 或 `deepseek` 模式。

### 模拟模式

模拟模式根据输入生成确定且符合正式 JSON 结构的结果。它用于离线演示、自动测试和 API 余额不足时的开发，不伪装成真实模型结果；界面始终显示当前运行模式。

### DeepSeek 模式

DeepSeek 模式使用 `deepseek-flash` 和官方 OpenAI 兼容端点。API Key 只从环境变量读取。模型名称、基础 URL、超时和价格保留为配置项，方便价格或模型名称变化时调整。

### 结构化输出

三类调用分别使用固定结构：

- 匹配：分数、推荐理由、证据、风险
- 沟通：邮件主题、正文、合作 brief
- 内容检查：通过项、缺失项、风险、修改建议、来源

响应必须经过 Pydantic 校验。解析或校验失败时重试一次；再次失败则记录错误并停止该动作。

### 规则筛选与评分

候选人必须同时满足市场、平台、粉丝量范围、单人预算和关键字段有效性要求。类别不完全匹配时允许保留，但降低规则评分并显示提示。规则评分为 0 到 100 分，由市场、平台、类别、粉丝量适配度、互动率和预算余量组成；具体权重作为代码常量并在项目说明中公开。

### RAG

系统通过 SQLite FTS5 从 `knowledge_docs` 检索最相关的三段资料，把正文和来源标签加入模型上下文。创作者结构化筛选不使用 RAG。第一版使用全文检索而非向量检索，因为语料规模小且需要可解释来源。

## 错误处理与安全边界

- API 请求设置超时，失败后最多重试一次。
- 模型失败不得改变审批状态或覆盖已有草稿。
- API Key 不写入源码、数据库、日志或浏览器。
- `.env` 不进入版本控制；提供 `.env.example`。
- CSV 限制扩展名和文件大小，并逐行验证字段。
- 页面输出默认转义用户和模型文本，避免执行提交内容。
- 数据库操作使用参数化查询或 ORM，不拼接用户 SQL。
- 删除和覆盖操作必须限制在当前项目数据范围内。
- 第一版没有多用户登录，因此不声称具备真实租户隔离或生产级权限系统。

## 验收标准

- 执行项目根目录的 `./run.sh` 即可初始化数据库并启动本地服务。
- 全新数据库可以自动初始化并载入示例数据。
- 无 API Key 时，模拟模式完整走通主流程。
- 配置 DeepSeek Key 后，无需改代码即可切换真实模型。
- CSV 导入能够报告重复、缺失、过期和无效字段。
- 硬条件不合格的创作者不会进入模型推荐列表。
- 模型结果经过结构校验并显示来源。
- 邮件必须人工批准，模型不能自动改变批准状态。
- 模型失败会记录错误，不会破坏现有数据。
- 20 个固定案例可以重复运行并显示指标。
- 自动测试覆盖数据清洗、规则筛选、审批、结构校验和失败降级。
- 页面在常见桌面宽度和窄窗口下可用。

## 明确不做

第一版不实现：

- 真实邮件发送
- 社交媒体爬虫或第三方平台登录
- 真实客户或创作者数据
- 多用户账号、角色或生产级权限
- 自动对外执行动作
- 多 Agent 编排
- 向量数据库
- 实时协作
- 移动端原生应用

## 生产化升级路径

如果系统进入真实使用，应优先增加身份认证与角色权限、PostgreSQL、后台任务、真实邮件或飞书集成、密钥托管、监控告警、数据保留策略和人工审核审计。只有当知识库规模或语义召回质量证明全文检索不足时，才引入向量检索。
