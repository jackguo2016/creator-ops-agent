# Creator Ops Agent 项目说明

本文介绍第一版受控工作流。2026-10-03 的历史修复记录为 66 项自动测试通过，详见 [FIXES_CN.md](FIXES_CN.md)；2026-10-04 的全量验证记录为 116 个测试实例（第一版 84、第二版 32），详见 [复查记录](RECHECK_2026-10-04_CN.md)。数量包含参数化实例；业务评测仍是下文的 20 个虚构案例。这些结果不代表真实模型判断质量或生产就绪，重跑测试时以实际输出为准。

## 1. 这个项目解决什么问题

海外创作者营销并不是“找几个人、发几封邮件”这么简单。团队要把客户目标转成筛选标准，从不同来源整理创作者数据，比较报价和内容风格，沟通合作要求，检查交付内容，再把过程和结果留档。人工处理时，最常见的问题不是某一步完全不会做，而是信息散落、重复复制、判断口径不一致，以及遗漏披露或截止时间等细节。

这个演示把上述流程压缩成一个单机工作台：

```text
项目 Brief
   ↓
CSV 导入、校验、去重
   ↓
硬条件淘汰 → 透明规则评分 → 模型解释
   ↓
选择创作者 → 英文外联草稿 → 人工批准
   ↓
交付文案审核 → 风险标签与修改建议
   ↓
Token / 耗时 / 成本日志 + 20 个固定评测案例
```

面试时最重要的定位是：它不是要替代项目经理，也不是一个会自行行动的“全自动 Agent”。它把适合自动化的重复工作交给系统，把预算、最终选择、外联批准和风险处理留给人。

## 2. 为什么先规则、后大模型

模型擅长处理自然语言、总结信息和给出解释，但不应该决定不可违反的业务边界。例如目标市场必须是美国、平台必须在指定列表、报价不能超过单人预算、数据不能过期。这些条件用普通代码判断更便宜、更快，也更容易测试。

因此匹配分成三层：

1. **硬条件筛选**：市场、平台、粉丝区间、报价、关键字段和数据质量。任何一项失败就不进入模型。
2. **透明规则分**：类别匹配、粉丝区间适配度、互动率和预算余量组成 100 分。页面公开展示权重。
3. **模型解释**：只处理合格候选人，基于 Brief 和检索到的知识给出分数、推荐理由、证据和风险。

这套分层让预算判断可以明确测试，不必依赖模型每次“自行理解”。输入变化后，旧选择和评分会失效，草稿保留为不可批准的历史；后续访问会重新计算规则。选择、生成与批准入口复核当前硬条件，模型返回后也检查输入快照，防止等待期间发生变更。

当前匹配页未运行 AI 时按规则分，运行后按 AI 分重排，规则分用于补充与同分排序。总预算字段仍只是保存，尚未实现累计合作费用控制或币种换算。

## 3. 数据模型和数据流

SQLite 中的主要表如下：

| 表 | 作用 |
|---|---|
| `campaigns` | 项目 Brief、预算、受众、平台、交付要求和限制。 |
| `creators` | 清洗后的创作者资料；平台与标准化 handle 联合去重。 |
| `matches` | 硬条件结果、规则分、模型分、依据、风险与选择状态。 |
| `drafts` | 英文外联主题、正文、Brief、待批准/已批准状态。 |
| `content_reviews` | 原始交付内容、链接、发布时间和结构化审核结果。 |
| `knowledge_docs` / FTS5 | 产品事实、披露规范、语气和交付检查清单。 |
| `model_runs` | Provider、模型、用途、Token、耗时、成本和错误摘要。 |

CSV 进入系统时会先检查必填列、数字格式、空 handle 和数据新鲜度，再按平台与 handle 去重。重复行保留更新时间较新的记录，并补回旧记录中仍然有效的邮箱，避免简单覆盖造成信息丢失。

## 4. FTS5 是什么，为什么这里不用向量数据库

FTS5 是 SQLite 自带的全文搜索。这个演示只有六份很短的知识文档，关键词非常明确，例如 `#ad`、medical claims、battery、delivery。FTS5 已经可以在本机快速找到相关条目，不需要额外服务、Embedding 费用或向量索引维护。

每次模型调用最多带入三条检索结果，并保留 `source_label`。这样做同时解决三个问题：

- 上下文更短，成本更低；
- 提示模型引用已有来源，并验证返回标签属于本次实际带入的资料；
- 页面可以告诉使用者结论依据的是“产品事实”还是“披露规范”。

来源标签存在不等于证据已核实。成员校验已实现，资料内容是否支持结论仍要单独判断。

如果生产环境扩展到成千上万份、多语言且语义相近的材料，再比较混合检索或向量数据库。当前数据量下提前引入向量基础设施只会增加部署和解释成本。

## 5. 模型接入到底做了什么

`LLMClient` 对上层暴露三个业务动作：候选人解释排序、英文外联生成、交付内容审核。Mock 和 DeepSeek 共用相同输入输出结构，因此界面和数据库不需要知道底层是哪种模式。

真实调用使用 Chat Completions，并要求返回 JSON object。返回后由 Pydantic 验证：例如分数必须在 0–100，主题和正文不能为空，多余字段被拒绝。HTTP 错误、JSON 错误或结构错误只重试一次；再次失败就明确报错，而不是把坏结果当成成功。

Mock 是固定规则实现。同一输入始终得到同一结果，适合零成本开发、测试和排练。品牌名读取当前 Brief，但电池、医疗词和首五秒政策仍是示例规则；改品牌不会同步替换知识库，不能把它当通用审核器。

Pydantic 只保证可读取的字段与约束，不证明事实正确。空 `choices` 等异常响应已纳入受控错误处理。

## 6. 人工审批为什么是核心功能

生成外联稿后，数据库状态一定是 `pending`。只有使用者点击“人工批准”后才会变成 `approved`，而且演示版没有任何发送邮件的代码。

这不是一个缺失功能，而是明确的产品边界：对外发送代表公司立场，涉及价格、承诺和品牌声誉，不应由模型直接完成。生产版即使接入邮件，也应继续保留审批人、时间、版本和撤回记录。

同样，内容审核输出的是“辅助判断”：系统标出缺少 `#ad`、医疗宣称、错误电池时长、链接缺失或发布时间超期等问题，最终是否接受仍由项目负责人决定。它只读取文字和链接字符串，不访问链接或检查视频。文案写了“首五秒展示产品”不代表画面已做到；问题标签为空也可能仍有待核实提示。

## 7. 评测目前能检查什么

评测文件固定包含 20 个虚构案例：

- 10 个创作者匹配案例，覆盖理想候选人、超预算、粉丝上限、错误市场、错误平台、类别不匹配、高互动备选和过期数据；
- 10 个内容审核案例，覆盖缺少披露、医疗宣称、产品缺失、链接缺失、延期、错误电池宣称、首五秒未展示产品，以及完全合格内容。

指标含义：

- **Top-1 命中率**：最高分候选人是否符合预期；
- **问题标签召回率**：应发现的问题中，实际发现了多少；
- **问题标签精确率**：报出来的问题中，有多少确实应该报告；
- **审核标签完全一致率**：整组标签是否符合人工预期，包含无问题案例；
- **结构化输出成功率**：模型结果是否通过约束校验；
- **平均耗时与估算成本**：一次评测的运行代价。

旧指标有盲点：两名候选都能进入前五，多报标签也能获得满召回。本轮改为 Top-1、增加精确率和完全一致率，并与真实页面共用检索链路。恒定 0 分并全报标签的退化响应现在得到 Top-1 50%、精确率约 12.86%、完全一致率 0%，不会再获得全部满分。

确定性 mock 在当前 20 案例上的五项指标都是 100%，只说明自建回归集符合预期。“结构化成功率”是重试后的最终成功率，不是首次格式正确率；完整真实模型质量评测尚未运行。

## 8. 成本如何计算

接口响应返回输入和输出 Token 数。项目按以下公式记录估算美元成本：

```text
输入 Token / 1,000,000 × 输入单价
+ 输出 Token / 1,000,000 × 输出单价
```

默认估算配置为 `$0.30 / 1M` 输入与 `$1.20 / 1M` 输出。每次约 3,000 输入和 500 输出 Token 时，一次请求约 `$0.0015`。这不是整个工作流的固定费用：示例有 20 名合格候选，全量解释是 20 次，加一份外联和一份审核，共 22 次，按上述假设约 `$0.033`，不含重试。

当前实现累计各次响应已返回的用量，覆盖验证失败和重试；单个用量字段异常时，另一个有效字段仍会累计，未知部分标记 `usage_unknown`。以前的日志不会自动补齐。因此估算仍不是账单或上限，需与控制台核对。真实价格以[DeepSeek 官方价格](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)为准；排练用 mock，只选少量样例调用真实模型。

## 9. 失败和安全如何处理

- API Key 只从环境变量读取；
- 上传文件限定 CSV 且不超过 1 MiB；
- SQL 全部使用参数化查询；
- 新模型日志不保存完整 Prompt、正文、Authorization Header 或异常原文；错误只留类型、状态码、尝试次数等安全元数据；
- 模型失败不创建成功的内容审核记录；
- 输入更新会使旧匹配、选择和草稿失效，模型返回后也检查输入变化；
- 高影响外联保持人工审批；
- 数据是虚构的，不应把真实个人资料直接放入公开演示库。

## 10. 我在面试中应该怎么概括技术选择

可以用这段话：

> 我没有把 Agent 理解成“接一个模型接口”。我先把真实工作拆成可验证的状态流：结构化 Brief、数据清洗、硬规则、模型解释、人工审批、内容审核和运行评测。确定性问题由代码负责，语言任务交给模型，涉及对外行动的步骤保留人工确认。为了让演示低成本且可重复，我做了 mock/DeepSeek 双模式、FTS5 小型知识检索、结构化输出校验和 20 个固定案例。

## 11. 生产化升级顺序

1. 登录、组织隔离和角色权限；
2. Postgres、迁移工具、备份与审计日志；
3. 异步任务队列、幂等键、限流和失败重放；
4. 接入 CRM、邮件和社媒数据源，并保留审批；
5. 对敏感字段做加密、保留期限和删除机制；
6. 用脱敏真实案例扩充离线评测，并监控线上反馈；
7. 知识量明显增大后再评估混合检索或向量方案。

演示版没有做登录、真实发信、爬虫、向量数据库和多 Agent；它们尚不属于当前演示范围。先修已确认的正确性问题并验证工作流，再根据真实需要增加能力。不要把“未实现”包装成“已经掌握但故意不做”。
