# 五分钟演示脚本

## 演示前准备

第一次从新克隆开始，以下假设文件夹名为 `creator-ops-agent`。在它的父目录执行；若文件夹名不同，替换第一行：

```bash
cd creator-ops-agent
LLM_PROVIDER=mock ./run.sh
```

1. 打开 `http://127.0.0.1:8000`，确认页面右上角为 `mock`；
2. 首次启动可能联网安装依赖；MOCK 不需要 API Key，也不会调用模型服务。显式 `LLM_PROVIDER=mock` 优先于已有 `.env`，适合后续重复排练；
3. 准备好 `data/creators.csv`；
4. 内容审核示例先复制到剪贴板：

```text
LumaSip cures dehydration and has a 30-day battery. Link in profile.
```

5. 第二次展示真实 API 时再切换 DeepSeek；第一次面试演示不要把成功与否押在网络上。
6. 如果此前用过真实模式，在服务终端按 `Control + C`，回到项目根目录重新执行 `LLM_PROVIDER=mock ./run.sh`，刷新后再次确认 `mock`。修改 Brief 或报价会清除旧选择、使旧草稿失效，需要重新筛选和生成。
7. 已实现 AI 重排和有效的误报指标，但回归结果不等于真实模型质量已达标。

## 0:00–0:30｜业务背景

打开“项目总览”。

可以这样说：

> 这是一个海外创作者合作工作台。实际团队需要反复整理候选人、核对预算、写英文外联、检查交付内容。我把它做成一条可追踪的工作流。这里的 Agent 不会擅自发邮件，而是在确定性规则和人工审批之间处理适合大模型的语言任务。

指出页面右上角的 `mock` 标签：

> 为了让开发和演示可重复，我做了 mock 和 DeepSeek 双模式。现在是零成本 mock，但走的是同一套业务接口和数据库流程。

## 0:30–1:05｜Brief 与数据导入

进入“项目 Brief”，快速指出：美国市场、TikTok/YouTube、粉丝区间、单人预算、截止日期、`#ad`、禁止医疗宣称、首五秒展示产品。

可以这样说：

> Brief 不是只保存一段 Prompt，而是拆成机器能执行的字段。这样预算和平台可以由代码严格判断，自由文本再交给模型理解。

进入“创作者库”，导入 `data/creators.csv`。

> CSV 导入会校验缺失字段、过期报价和重复 handle。重复记录保留更新的一行，同时补回仍然有效的旧邮箱。这里所有资料都是虚构数据。

## 1:05–1:55｜匹配与解释

进入“智能匹配”，点击“重新运行规则筛选”，再点击“运行 AI 解释排序”。

> 我先做硬过滤，合格候选人再打规则分。模型补充评分、解释与风险，页面随后按 AI 分重排。修改预算或资料会使旧选择和草稿失效；模型等待期间发生修改，旧结果也会被拒绝。这样可以把状态边界放进代码和测试，而不只写在提示词里。

指向“被规则排除”区域，再指向 AI 分和推荐语。

> 这种分层比让模型一次性做所有判断更便宜、更稳定，也更容易定位错误。

选择一名创作者。

## 1:55–2:50｜外联与人工批准

在“沟通与交付”点击“生成英文外联草稿”。展开 Brief，指出英文主题、正文和交付要求。

> 这是模型适合做的部分：根据结构化项目字段和创作者资料生成英文初稿。但草稿默认是 pending，系统没有发信能力。

点击“人工批准”。

> 点击后才记录 approved 和时间。生产版可以在这个确认点后接邮件系统，同时记录审批人和版本。把人工确认放进产品流程，而不只是写在提示词里，是我对 Agent 安全边界的理解。

## 2:50–3:30｜内容审核

把准备好的不合格文案粘贴到“创作者提交内容”，填写任意测试链接和截止日前的时间，点击“运行内容审核”。

指出结果中的：

- `missing_disclosure`；
- `medical_claim`；
- `unsupported_battery_claim`；
- `missing_visible_product`；
- 修改建议和依据来源。

> 模型返回的是经过 schema 格式校验的列表，来源标签也会检查是否属于本次资料。但格式与来源成员关系都不能证明结论正确；这里只检查提交文字，没有读取视频或访问链接。

## 3:30–4:10｜日志与评测

进入“日志与评测”，点击运行 20 个案例。

> 日志记录各次重试已返回的用量，不存原始异常或模型正文；未知用量会标记。20 个案例检查 Top-1、漏报、误报和标签完全一致率，包含合格文案。mock 回归通过不等于真实模型准确，费用也要与控制台核对。

## 4:10–5:00｜设计取舍与收尾

可以这样收尾：

> 这个知识库只有六份短文档，用 SQLite FTS5 做关键词检索；当前流程由代码和人控制，不是自主工具调用的 Agent。下一步先修已确认的状态与评测问题，不急着增加组件。真实使用时再按风险补权限、数据授权、审批版本、备份和任务恢复。

最后一句：

> 这个项目想证明的是，我能把业务流程拆成确定性逻辑、模型能力和人工决策三部分，并用评测和日志验证它，而不只是把 API 接到一个聊天框里。

## 如果现场时间只剩两分钟

只展示三件事：

1. 匹配页：不合格候选人被硬规则排除；
2. 外联页：模型生成后必须人工批准；
3. 日志页：20 个案例和 Token/成本记录。

这三处最能对应 Agent 应用工程师职位所关心的全栈交付、模型集成、可靠性和产品判断。
